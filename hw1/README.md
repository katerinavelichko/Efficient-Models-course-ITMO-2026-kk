## Вывод формул

Обозначения:
S - сторона изображения, B - батч, h_l = S/d_l - сторона карты признаков слоя l,
4 байта на элемент (FP32).

### FLOPs(S, B)

1 MAC = 2 FLOPs  
сложение bias = 1 FLOP  
ReLU = 1 FLOP на элемент (сравнение)  
MaxPool $k\times k$ = $k^2-1$ сравнений на выход  
GlobalAvgPool = 1 сложение на вход + 1 деление на канал

Свертка: $F_{conv} = 2\,k^2\,C_{in}\,C_{out}\,h_{out}^2\cdot B

| Слой | FLOPs на изображение |
|---|---|
| conv1 | $2\cdot 49\cdot 3\cdot 32\cdot (S/2)^2 = 2352\,S^2$ |
| conv2 | $2\cdot 25\cdot 32\cdot 64\cdot (S/4)^2 = 6400\,S^2$ |
| conv3 | $2\cdot 9\cdot 64\cdot 128\cdot (S/8)^2 = 2304\,S^2$ |
| conv4 | $2\cdot 128\cdot 256\cdot (S/8)^2 = 1024\,S^2$ |
| conv5 | $2\cdot 9\cdot 256\cdot 256\cdot (S/16)^2 = 4608\,S^2$ |
| conv6 | $2\cdot 256\cdot 512\cdot (S/16)^2 = 1024\,S^2$ |
| 6 x ReLU | $(8+4+2+4+1+2)\,S^2 = 21\,S^2$ |
| MaxPool | $8 \cdot 2S^2 = 16\,S^2$ |
| AvgPool | $2S^2 + 512$ |
| fc1 + ReLU + fc2 | $(2\cdot512\cdot256+256) + 256 + (2\cdot256\cdot100+100) = 313\,956$ |

$$\boxed{\mathrm{FLOPs}(S,B) = B\,(17\,751\,S^2 + 314\,468)}$$

Свертки дают $17\,712\,S^2$ (99.8%), поэтому поэлементные операции в FLOPs практически не видны,
зато они видны в трафике памяти (ниже). Проверка: часть conv+linear без bias
($17\,712\,S^2 + 313\,344$) совпадает с `torch.utils.flop_counter.FlopCounterMode` **точно** на всех точках.

### Memory(S, B)

Соглашение из чата курса: веса + вход + **сумма всех активаций всех слоев** (в аналитической модели ничего
не освобождается). In-place ReLU и Flatten новых тензоров не создают.

Элементы активаций на изображение: вход $3S^2$, conv1 $8S^2$, pool $2S^2$, conv2 $4S^2$, conv3 $2S^2$,
conv4 $4S^2$, conv5 $S^2$, conv6 $2S^2$, голова $512+256+100=868$, итого $A(S) = 26S^2 + 868$.

$$\boxed{\mathrm{Memory}(S,B) = 4\,\big(N + B\,(26\,S^2 + 868)\big) = 4\,161\,296 + B\,(104\,S^2 + 3\,472)\ \text{байт}}$$

Измеряемая величина - `torch.cuda.max_memory_allocated()`, т.е. максимум памяти, занятой тензорами
**одновременно**, поэтому точного равенства не ожидается. Для обсуждения используется оценка "по времени
жизни": в eager-PyTorch под `inference_mode` тензор освобождается, как только на него нет ссылок; одновременно
живы веса, вход сети и вход + выход текущего слоя, максимум - на MaxPool ($3S^2+8S^2+2S^2$):
$\mathrm{Memory}_{live} = 4\,(N + 13\,B\,S^2)$ - ровно вдвое меньше суммы по $S^2$-члену.

Не учтены (формула не зависит от калибруемых параметров): workspace cuDNN/cuBLAS (выделяется через
caching allocator и попадает в `max_memory_allocated`), округление аллокаций до 512 Б.

### Bytes moved (вспомогательная функция)

Каждый кернел один раз читает свои входы (активации + веса) из DRAM и один раз пишет выход; кэш между
кернелами не переиспользуется.

| Слой | Элементов на изображение |
|---|---|
| conv1 / relu1 / pool | $3+8$ / $2\cdot8$ / $8+2$ ($\times S^2$) |
| conv2 / relu2 | $2+4$ / $8$ |
| conv3 / relu3 | $4+2$ / $4$ |
| conv4 / relu4 | $2+4$ / $8$ |
| conv5 / relu5 | $4+1$ / $2$ |
| conv6 / relu6 | $1+2$ / $4$ |
| avgpool | $2S^2 + 512$ |
| голова | $768 + 512 + 356$ |
| веса (на батч) | $N$ |

$$M(S,B) = 4\,(91\,B\,S^2 + 2\,148\,B + N) = 364\,B\,S^2 + 8\,592\,B + 4\,161\,296\ \text{байт}.$$

Арифметическая интенсивность всей сети $\approx 17\,751/364 \approx 49$ FLOP/байт - у T4
(8.1 TFLOP/s FP32, 320 GB/s) точка перегиба roofline ≈ 25 FLOP/байт, т.е. сеть в целом compute-bound,
но по слоям это не так: ReLU/MaxPool/AvgPool - 0.1-0.4 FLOP/байт (чисто memory-bound), conv1 (3 входных канала)
≈ 53 FLOP/байт по формуле, но cuDNN для него неэффективен.

### Latency(S, B, θ)

Для каждого кернела $l$ (17 штук: 6 conv, 7 ReLU, maxpool, avgpool, 2 linear) время - "мягкий максимум" трех
ограничений: минимальное время кернела (launch/dispatch), вычисления, память:

$$
T(S,B;\theta) = t_0 + \sum_{l} \Big\| \big(t_{launch},\ \tfrac{F_l(S,B)}{R_l},\ \tfrac{M_l(S,B)}{BW}\big) \Big\|_p ,
\qquad \|x\|_p = \Big(\sum_i x_i^p\Big)^{1/p}.
$$

$\theta = (t_0, t_{launch}, BW, p, R)$:
- $t_0$ - фиксированная стоимость прохода (Python, диспетчер, синхронизация)
- $t_{launch}$ - нижняя граница времени одного кернела (launch-bound режим)
- $BW$ - эффективная пропускная способность DRAM
- $R$ - эффективная производительность; в **global**-варианте одна на все слои (5 параметров),
  в **per-layer** - своя для каждой свертки + общая для остальных (4 + 7 параметров): cuDNN для разных форм
  выбирает разные алгоритмы (implicit GEMM, Winograd, FFT) с разной эффективностью
- $p$ - степень перекрытия: $p\to\infty$ - жесткий roofline-max, $p=1$ - времена складываются
  (нет перекрытия вычислений и памяти). $p$ подбирается

Максимум не раскрываем - это и есть модель; параметры подбираются по данным (`scipy.optimize.least_squares`
по $\log T$, т.е. по относительной ошибке, все параметры положительны через лог-параметризацию,
несколько стартов). Калибровка - только базовая сетка 7x9 = 63 точки; валидация - все точки со случайными
$S$ или $B$ (69 точек). Основной вариант - **global**, выбран заранее (валидация для выбора не используется);
per-layer считается для сравнения.

Режим (`equations.regime`) - какой член суммарно доминирует: launch/overhead, память или вычисления.

### Energy(S, B, θ)

Энергия всего GPU за один проход = статическая мощность x время + динамическая энергия на операции и байты:

$$
E(S,B;\theta_E) = P_{static}\cdot T(S,B;\theta) + e_{flop}\cdot \mathrm{FLOPs}(S,B) + e_{byte}\cdot M(S,B).
$$

$\theta_E = (P_{static}, e_{flop}, e_{byte})$ + θ латентности. $T$ - **предсказанное** время, поэтому формула
зависит только от $(S,B)$. Коэффициенты - неотрицательный МНК по относительной ошибке (`scipy.optimize.nnls`).

Замер: аппаратный счетчик `nvmlDeviceGetTotalEnergyConsumption` (мДж, Volta+; если недоступен -
интегрирование `nvmlDeviceGetPowerUsage` с шагом 5 мс), окно ≥ 2 с непрерывных проходов,
энергия / число проходов. Idle-мощность меряется отдельно и сравнивается с $P_{static}$.

### Замеры

- Latency: 3 прогрева (первый - под `FlopCounterMode`), затем $n=\mathrm{clip}(0.5\text{ с}/t_1, 10, 300)$ проходов,
  каждый: `synchronize -> perf_counter -> forward -> synchronize`; медиана (+ p25/p75).
- Memory: `reset_peak_memory_stats()` -> один проход -> `max_memory_allocated()` (абсолютное значение:
  веса + вход + workspace + активации). Отдельно пишется `memory_allocated()` до прохода.
- OOM: `torch.cuda.OutOfMemoryError` ловится, конфигурация пишется как `status=OOM`.
- Порядок конфигураций случайный (чтобы тепловой дрейф/троттлинг не коррелировал с $S,B$).
- Сетка: $S$ = 32, 64, 128, 224, 256, 384, 512 + 4 случайных кратных 16; $B$ = 1…256 (степени 2) + 3 случайных
  не-степени двойки (seed=0 -> $S$ = 176, 288, 336, 400; $B$ = 9, 50, 209).
- **OOM** На T4 (14.46 ГиБ свободно) базовая модель при $B\le256$ в память
  укладывается: $\mathrm{Memory}(512,256) = 6.5$ ГиБ. Поэтому дополнительно измерены $S\in\{384,512\}$,
  $B\in\{384, 512, 768, 1024, 1280, 1536, 2048\}$ (`is_probe=1`, в калибровку и валидацию не входят).
  Архитектура модели не менялась.

## Обсуждение: где и почему формулы ломаются

**FLOPs.** Формула получилась точной: Conv+Linear совпадают с `FlopCounterMode` на всех 132 точках, а вклад ReLU и pooling очень мал.

**Memory.** Аналитическая модель складывает все активации и поэтому работает скорее как верхняя оценка. Реальный пик отличается, потому что промежуточные тензоры освобождаются, а CUDA/cuDNN могут использовать дополнительный workspace. Поэтому на маленьких входах формула заметно недооценивает память, а на больших иногда переоценивает ее. При этом все реальные OOM были предсказаны, но появились 4 ложных OOM. Разные convolution algorithms действительно могут иметь разные требования к памяти. 

**Latency.** При маленьких S и B наблюдается launch-bound режим: время почти не зависит от FLOPs и держится около 0.5 мс. При увеличении B*S^2 время начинает расти почти линейно. Модель помечает большую часть этой области как memory-bound, но FLOPs и BytesMoved здесь растут почти одинаково, поэтому fitting не может надежно разделить memory- и compute-bound ограничения. Параметры BW и R поэтому следует рассматривать как эффективные коэффициенты модели, а не реальные характеристики GPU.

Основные ошибки latency возникают при больших batch: производительность GPU меняется из-за частот/нагрева и выбора kernel для конкретной формы тензора. При `cudnn.benchmark=False` PyTorch не перебирает все алгоритмы измерением, тогда как `benchmark=True` как раз тестирует несколько вариантов и выбирает быстрый для данного размера входа. Особенно плохо модель работает для S=32 и больших B, где карты признаков слишком малы для эффективной загрузки GPU. Per-layer модель уменьшает validation MAPE с 18.5% до 14.8%.

**Energy.** Энергия в основном следует за latency, поскольку мощность GPU под нагрузкой меняется меньше, чем время выполнения. Поэтому ошибки Energy возникают примерно на тех же точках, что и ошибки Latency.

**Вывод.** FLOPs предсказываются практически точно. Memory полезна как консервативная оценка OOM, но не описывает реальное управление памятью. Latency и Energy переносятся на unseen (S,B) с ошибкой примерно 15-18%. Главные причины расхождений - изменение эффективности GPU при разных размерах batch, выбор convolution kernels и слишком простая модель с постоянными BW и R.
